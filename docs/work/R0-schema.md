- R2: invites are ready for the activation flow: create the user and an INVITED membership, then an `invites` row with the token's SHA-256; the signed-out accept step reads it with `db.forInvite(tokenHash)`, then works in business scope.
- I02 (Ibrahim, client profile API): `client_profiles.dob_enc` and `ssn_enc` hold encrypted values only, never plain SSN or date of birth. Write them only through the KMS-backed encrypt helper (Rasel assigns that helper to R5); keep only `ssn_last4` in plain text.
- R5 (secure documents):
  - Store objects at `tenant/<business_id>/...` (a CHECK on `documents.s3_key` enforces the firm prefix; it matches the IAM policy `tenant/*`).
  - The key is fixed once the row exists (the database refuses a change). Record the scan result on the row and never move objects; if R5 ever needs to move objects, it asks R0 first.
  - Create the row as `PENDING`; the scanner sets `scan_status` and `scanned_at` once.
  - A hard delete of a `documents` row must also remove the object's old versions, because the documents bucket is versioned. The alternative is a lifecycle rule that expires noncurrent versions.
  - Begin Online uploads (`lead_uploads`) follow the same rules: `tenant/<business_id>/...` (e.g. `tenant/<id>/leads/<uuid>`), start `PENDING`, scan result set once, key fixed. At lead conversion the API inserts a `documents` row with `lead_upload_id` and the same key, file and scan result; the object stays where it is.
- R6 (email and SMS sender): `notification_deliveries` is the outbox.
  - Process each firm's QUEUED rows in that firm's business scope; there is no cross-firm scope for firm data.
  - Look up the address or number at send time; the table stores neither, nor any content.
  - Mark SENT with `sent_at` and the provider message id, or FAILED with a short error code and `attempts + 1`, then back to QUEUED to retry. Mark SKIPPED when the person's preference is off or there is no address or number.
  - ACCOUNT notices ignore preferences.
  - Client note reminders: in each firm's business scope (no actor), pick `client_note_reminders` with `remind_at <= now()` and `reminded_at IS NULL`. Notify the note's owner (`user_id`) without any note text, then set `reminded_at`.
- T03 (team API): a firm always keeps an active owner, in the database. Demoting, deactivating or removing the last active owner fails with SQLSTATE `FV001`, message `LAST_ACTIVE_OWNER: ...`. Catch it with `isDbError(error, 'LAST_ACTIVE_OWNER')` from `@firmivra/db` and answer 409 with that code, so the screen can say "Make someone else an owner first". To hand over ownership, promote the new owner first, then change the old one.
- R3 (business settings API): `business_settings.accent_color` is optional (`#rrggbb`, same check as `brand_color`). Send the default accent colour when it is empty.
- R3 (client sign-up): `verification_codes` is ready, in business scope (the firm from the portal route).
  - Send: insert `channel`, `target` (the exact lower-case email or E.164 phone), `codeHash` (hex HMAC-SHA256 of the code with the server key) and `expiresAt` at most 15 minutes ahead. Up to 1 minute over is trimmed.
  - The database sets `createdAt` from its clock; use it for the 45-second resend gap.
  - Check: add 1 to `attempts` on every try. The database does not cap attempts: lock out at your limit.
  - Accept: set `consumedAt` (any value; the database stores its own time). Only the newest unexpired code for that account and channel can be used, and then never changes.
  - Before accepting, compare `target` with the account's current email or phone.
  - Pending approval queue: `client_accounts (business_id, status)` is already indexed.
- Portal API (client notes routes, Messages and Notes): use `db.forBusiness(businessId, { actorUserId: <signed-in client user id> })` for `client_private_notes` and for creating a reminder. Without the actor the database returns no notes and refuses writes. Staff routes never pass a client's id as actor.
